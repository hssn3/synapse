# ADR 0003: موتور فرم‌ساز مبتنی بر JSON Schema و نسخه‌بندی قطعی

## وضعیت (Status)
پذیرفته‌شده (Accepted)

## زمینه (Context)
هدف اصلی و کانونی پروژه، تبدیل سامانه به یک **پلتفرم Form Builder Enterprise** است.
پیش از این، فرم‌ها به صورت کدهای دستی در موتور RPG یا HTML ثابت با فیلدهای دستی ساخته می‌شدند. برای هر فرم جدید، نیاز به تغییر کدهای فرانت‌اند و بک‌اند و مایگریشن جدول دیتابیس بود.
بیمارستان‌ها روزانه ده‌ها فرم جدید (چک‌لیست‌های ترالی، ارزیابی، نظرسنجی، فرم‌های کمیته و شیفت) نیاز دارند که باید بدون کامپایل یا تغییر کد توسط ادمین ساخته و مدیریت شوند.

## تصمیم (Decision)
طراحی و پیاده‌سازی **Enterprise Form Engine**:
1. **طراحی مبتنی بر Schema (JSON Schema + Ajv)**:
   - تعریف فرم با JSON استاندارد شامل فیلدها، نوع داده، اعتبارسنجی‌ها، چیدمان و شروط نمایش.
2. **پشتیبانی از انواع فیلدهای بیمارستانی**:
   - `text`, `number`, `date`, `jalali-date`, `select`, `multi-select`, `file`, `signature`, `matrix`, `table`, `computed`, `conditional`
3. **موتور منطق شرطی (Conditional Logic DSL)**:
   - نمایش یا پنهان‌سازی فیلدها، الزامی شدن و محاسبات داینامیک بر اساس مقادیر فیلدهای دیگر (e.g. `show_if: { field: "has_allergy", equals: true }`).
4. **نسخه‌بندی تغییرناپذیر (Immutable Form Versioning)**:
   - جدول `forms` (اطلاعات کلی)، `form_versions` (نسخه، وضعیت draft/published/archived، اسکیمای کامل).
   - جدول `form_submissions` که همیشه شناسه `form_version_id` را دارد تا با تغییر فرم، داده‌های قدیمی تحریف نشوند.
5. **مجوزهای سطح فیلد (Field-Level Permissions)**:
   - اتصال فیلدها به قوانین دسترسی؛ به طوری که یک نقش بتواند فیلد را فقط ببیند (`read-only`)، دیگری بتواند پر کند (`editable`) و نقش ناظر بتواند امضا کند (`sign-only`).
6. **گردش کار یکپارچه (Workflow Binding)**:
   - مراحل وضعیت: `draft` -> `submitted` -> `under_review` -> `approved` -> `archived`.

## پیامدها (Consequences)
- صفر نیاز به تغییر کد برای تعریف یا تغییر فرم‌ها.
- تاریخچه دقیق تغییرات و حفظ یکپارچگی داده‌های تاریخی ثبت‌شده.
